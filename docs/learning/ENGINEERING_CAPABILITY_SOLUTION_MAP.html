1. Scope and interpretation

This document uses established systems, information-retrieval, software-engineering, security, and AI-system terminology. It distinguishes an engineering capability from the mechanism used to realize it. A capability answers “what must the system do?”; a mechanism answers “by what algorithm, data structure, protocol, design pattern, or control is that achieved?”

Important: an implementation mapping does not imply formal conformance to every cited standard or paper. Standards and research references identify the closest established engineering concept. 3. Knowledge ingestion, identity, and lifecycle

Implemented

3.1 Deterministic ingestion and parsing

Engineering concept

Staged ingestion pipeline with a ports-and-adapters source boundary. Acquisition, parsing, canonicalization, and persistence are separate responsibilities so source-system concerns do not determine knowledge identity.

How the mechanism works

Source connector → immutable RawKnowledgeRecord → MIME-aware deterministic parser → ExtractedKnowledgeText → canonical normalizer → version resolver → chunker → durable store

Parsing is deliberately deterministic: malformed or unsupported formats fail explicitly rather than silently invoking a model to repair content. This is a form of deterministic boundary processing.

Tropos mapping

  • Connector contract isolates acquisition.
  • Exact payload bytes and source metadata are retained as raw capture.
  • TXT, Markdown, HTML and DOCX use format-specific deterministic parsers.
  • Probabilistic extraction is kept out of canonical identity.

Alternative patterns

  • LLM-first parsing or document AI: higher format coverage, lower determinism.
  • Event-stream ingestion: appropriate when source change volume requires asynchronous processing.
  • CDC/change feeds: appropriate for database-backed source systems.

Validation

Parser contract tests, malformed-input tests, replay/idempotency tests, format-specific fixtures, and preservation of raw input identity.

3.2 Canonicalization and content fingerprinting

Engineering concept

Canonical representation converts semantically irrelevant representation differences into one stable form. A cryptographic content fingerprint then makes equality and change detection explicit.

How the mechanism works

Extracted text → Unicode normalization → line-ending normalization → structural blocks → stable serialization → SHA-256 → normalized_content_fingerprint

The key design principle is that the same representation used to compute identity also renders canonical text. This prevents “hash one thing, retrieve another” drift.

Tropos mapping

  • Unicode NFC, BOM removal, line-ending and whitespace normalization.
  • Headings, paragraphs and list items become ordered structural blocks.
  • Stable JSON serialization is hashed with SHA-256.
  • Formatting-only source changes can map to the same canonical version.

Related theory

This is conceptually related to canonical serialization and content-addressed storage. It is not Git/Merkle-tree implementation, but it applies the same separation between logical content identity and mutable location.

Standard RFC 8785 — JSON Canonicalization SchemeStandard Unicode Standard Annex #15 — Normalization FormsTropos ADR-004
Implemented

3.3 Content versioning and idempotency

Engineering concept

Content-based versioning, idempotent processing, and optimistic concurrency. Source version, exact payload identity, canonical content identity, and access state are intentionally different dimensions.

How the mechanism works

candidate canonical state ├─ same content + same policy → NO_CONTENT_VERSION ├─ same content + policy change → REFRESH_GOVERNANCE ├─ content change → CREATE_VERSION └─ normalization algorithm change → REBASELINE_REQUIRED

Strategy versioning is important: when the normalization algorithm itself changes, different fingerprints do not automatically prove business content changed.

Tropos mapping

CanonicalKnowledgeState tracks content fingerprint, normalization strategy version, and access fingerprint. Ingestion run identity also includes processing version so an upgraded pipeline can intentionally reprocess the same source.

Validation

Replay tests, formatting-only change tests, ACL-only change tests, concurrent expected-state checks, and explicit rebaseline outcomes.

Pattern Idempotent ReceiverTropos Canonical version resolution
Implemented

3.4 Chunking as evidence segmentation

Engineering concept

Passage segmentation converts canonical documents into retrieval units. Chunk design is a bias/variance trade-off: very small chunks improve local precision but lose context; very large chunks preserve context but dilute retrieval specificity and consume model context.

How the mechanism works

Canonical structural blocks → bounded grouping under chunk-size constraint → exact document offsets → stable chunk identity → lossless chunk-set validation

Tropos treats chunks as evidence units, not merely embedding inputs. Each chunk therefore retains exact offsets, source lineage, content fingerprint, access policy, and processing strategy versions.

Alternatives / extensions

  • Fixed-token windows with overlap.
  • Recursive/structure-aware splitting.
  • Topic segmentation such as TextTiling.
  • Semantic breakpoint chunking using embeddings.
  • Parent-child retrieval: small retrieval units with larger context expansion.

Validation

Chunk reconstruction, no gaps/overlaps, stable IDs, retrieval evaluation under multiple chunk-size/overlap configurations.

Paper Hearst — TextTiling: Segmenting Text into Multi-paragraph Subtopic PassagesTropos KnowledgeChunk invariants

4. Retrieval engineering

Implemented

4.1 Lexical retrieval: inverted index + BM25

Underlying theory

Lexical search belongs to classical Information Retrieval (IR). An inverted index maps each term to postings identifying the documents/chunks that contain it. Ranking then estimates how useful each matching document is for the query.

BM25 mechanics

BM25 combines term frequency, inverse document frequency, and document-length normalization. Rare query terms carry more discriminative value; repeated occurrences help with diminishing returns; long documents are normalized so length alone does not dominate.

query terms → FTS tokenizer → inverted postings → matching chunks → BM25(term frequency, inverse document frequency, length normalization) → ranked top-k

Tropos implementation

SQLite FTS5 supplies the full-text index and built-in BM25 ranking. This is especially suitable for exact identifiers, product names, error codes, policy terms, and high-overlap language.

Extensions

  • Field weighting: title/product/code fields can carry different weights.
  • Stemming/tokenizer changes.
  • Synonym/query expansion.
  • Move to Lucene/OpenSearch/Elasticsearch when distributed indexing or richer analyzers are justified.

Validation

Recall@k, MRR, nDCG for graded labels, exact-identifier cases, typo/synonym cases, and query-by-query error analysis.

Book Manning, Raghavan & Schütze — Introduction to Information RetrievalDocs SQLite FTS5 and BM25
V1

4.2 Dense retrieval: bi-encoder + vector similarity

Underlying theory

Dense retrieval represents queries and passages as vectors in a learned embedding space. A bi-encoder encodes query and document independently, making document vectors precomputable and query-time search efficient.

Mechanics

document chunk → embedding model → document vector (persist) query → same vector-space contract → query vector eligible document vectors → cosine similarity → sort → top-k

Vector-space compatibility is a contract: vectors from different embedding models, dimensions, or preprocessing strategies must not be silently mixed.

Tropos implementation

  • Embeddings are derived state, keyed by chunk identity + embedding strategy version.
  • Current V1 performs an exact scan over eligible vectors.
  • Cosine similarity is explicit in the embedding strategy.
  • Eligibility is resolved before similarity ranking.

Why exact search first

Exact nearest-neighbour search provides a deterministic quality baseline. It separates the question “does this representation retrieve the right evidence?” from “how do we search millions of vectors quickly?”

Validation

Recall@k/MRR/no-answer accuracy against BM25; model-migration tests; missing-index fail-closed behavior; latency versus corpus size.

Paper Karpukhin et al. — Dense Passage RetrievalTropos Dense Retrieval V1 deep dive
V1

4.3 Hybrid retrieval: Reciprocal Rank Fusion

Underlying theory

Data fusion / rank aggregation combines multiple retrieval systems. This is preferable to blindly adding raw BM25 and cosine scores because the scores are not calibrated onto the same statistical scale.

RRF mechanics

score(d) = Σ 1 / (k + rank_i(d)) BM25 ranked list ─┐ ├→ rank-only fusion → final ranking Dense ranked list ─┘

Documents appearing near the top of multiple systems accumulate contributions. Tropos uses a bounded candidate pool and then trims to the requested final top-k.

What RRF does not solve

RRF improves ordering; it is not an answerability or abstention algorithm. If both retrievers return irrelevant nearest neighbours, fusion can still rank irrelevant evidence.

Validation

Run the same versioned dataset through BM25, dense and hybrid; compare ranking metrics and no-answer behavior case by case.

Paper Cormack, Clarke & Büttcher — Reciprocal Rank FusionTropos Hybrid Retrieval V1
Deferred

4.4 Approximate nearest-neighbour indexing

Engineering problem

Exact dense search is O(N) over eligible vectors. At large N, vector search typically moves to Approximate Nearest Neighbour (ANN) methods that trade some recall for lower query latency.

HNSW

Hierarchical Navigable Small World builds a multilayer proximity graph. Search begins at sparse upper layers and progressively descends toward local neighbours. Important controls include construction quality, query candidate breadth, memory, and recall.

IVF / IVFFlat

An inverted-file index clusters vectors into lists. The query probes only selected nearby lists. More probes generally improve recall at higher latency.

Tropos extension strategy

Exact cosine baseline → scale rehearsal → define latency + recall targets → pgvector exact → pgvector HNSW / IVFFlat → compare recall/latency/filter correctness → consider managed service only if operational needs justify it

Important governed-search issue

ANN plus metadata/tenant filtering is not trivial. Some implementations scan ANN candidates then apply predicates; this can under-return eligible results. Partitioning, partial indexes, iterative scans, or filter-aware ANN can be required.

Paper Malkov & Yashunin — HNSWDocs pgvector — exact, HNSW, IVFFlat and filtering
Deferred

4.5 Reranking: two-stage retrieval

Underlying theory

Candidate generation and final ranking have different cost constraints. A two-stage retrieval architecture uses a fast retriever to find a bounded candidate set, then a slower, more expressive cross-encoder reranker scores query-document pairs jointly.

query → BM25 / dense / hybrid top 50 → cross-encoder(query, passage) for each candidate → relevance scores → final top 5

Why it can help

Bi-encoders compress query and document separately; cross-encoders can model token-level interactions between them, usually improving ranking accuracy at higher compute cost.

When Tropos should add it

Only when labelled evaluation shows that candidate recall is good but top-rank precision remains insufficient. If the right evidence never enters the candidate pool, reranking cannot recover it.

Validation

Compare nDCG/MRR/Recall@k before and after reranking, plus p95 latency, provider cost and abstention effects.

Paper Nogueira & Cho — Passage Re-ranking with BERT
Candidate

4.6 Query transformation and retrieval extension

Established patterns

  • Query expansion: add related terms to improve recall.
  • Relevance feedback / Rocchio: move the query representation toward relevant examples and away from irrelevant ones.
  • Multi-query retrieval: generate multiple formulations and fuse results.
  • HyDE: generate a hypothetical relevant document and embed that representation for retrieval.
  • Metadata filtering: constrain candidates by structured fields before/within ranking.

Engineering principle

Each transformation must be evaluated as an independent retrieval stage. Query rewriting can improve semantic recall but may also drift from the original intent and expand the authorization/egress surface.

Tropos criterion

Add only when labelled failure analysis identifies a query-understanding problem rather than a ranking, chunking, or evidence-sufficiency problem.

5. Evidence, provenance, and citations

Implemented

5.1 Evidence management: provenance + lineage

Established concept

Data provenance records where an information item came from, how it was transformed, and what identities/processes are related to it. W3C PROV models provenance around Entity, Activity, and Agent relationships.

Tropos technique

Tropos does not claim W3C PROV conformance, but the architecture follows the same provenance objective. A retrieved evidence item can be traced through stable knowledge/chunk identity to canonical content, source record/version, processing strategy, and access state.

source record/version → raw capture fingerprint → normalized content fingerprint → canonical document version → chunk ID + offsets → retrieval strategy/rank → EvidenceRef → generated artifact citation

Why the evidence object is separate from the index row

An index is a derived representation. The authoritative evidence object must survive reindexing, embedding-model migration, or retrieval-engine replacement. This is a classic separation between system of record and derived index.

Extensions

  • Explicit provenance graph.
  • Claim-level lineage.
  • Transformation activity records.
  • Source trust/quality metadata.
  • Reviewer/approval agent identity.

Validation

Lineage completeness, stable identifier tests, source-version traceability, no dangling references, and reconstruction of the source/evidence path for any output claim.

Standard W3C PROV-O — Provenance OntologyStandard W3C PROV-DM — Provenance Data ModelTropos Knowledge model
Identity correctness

5.2 Citation management: alias indirection + deterministic resolution

Engineering concept

The core technique is identifier indirection combined with referential integrity. The model receives short, prompt-local symbolic references; application code—not the model—owns durable identity.

How it works

Authoritative EvidenceRef objects ↓ construct request-local mapping E1 → EvidenceRef(chunk A, locator..., version...) E2 → EvidenceRef(chunk B, locator..., version...) ↓ prompt shows [E1], [E2] ↓ model returns citations ["E1","E2"] ↓ deterministic resolver: - reject blank alias - reject unknown alias - deduplicate - resolve to exact EvidenceRef ↓ persist/display stable citation identity

What this guarantees

Identity validity: the cited evidence existed in the request and resolves to a known governed object.

What this does not guarantee

Semantic citation correctness: the cited passage actually entails/supports the generated claim. This requires a separate attribution/entailment evaluation.

Industry/research analogue

Citation-enabled generation research separates citation presence, correctness, and completeness. ALCE formalizes citation-quality evaluation across those dimensions. Tropos’s resolver currently addresses the referential-identity layer; semantic support remains a stronger future evaluator.

Extension

generated claim → cited EvidenceRef(s) → NLI / LLM entailment evaluator → supported / partially supported / unsupported → citation completeness across all verifiable claims

5.3 Evidence sufficiency and selective generation

Engineering concept

Answerability asks whether an answer exists in the available context. Sufficient context is stronger than relevance: relevant evidence may still omit a critical fact. Selective prediction/generation allows a system to abstain when uncertainty or evidence insufficiency exceeds an accepted risk.

Tropos technique

Retrieved evidence → deterministic authorization/currentness/integrity gates → EvidenceSet → structured sufficiency judge required_facts supported_facts missing_facts contradictions → SUFFICIENT / INSUFFICIENT → generate or abstain

Why this is distinct from retrieval score

BM25/cosine/RRF tell us how candidates rank under a retrieval strategy. They do not prove that all facts required for a correct answer are present. Score thresholds therefore cannot substitute for sufficiency evaluation.

Validation

Human-labelled sufficiency cases, inter-reviewer agreement, false-sufficient rate, false-insufficient rate, answer accuracy stratified by sufficiency, and coverage-vs-risk curves.

Paper Sufficient Context — ICLR 2025 / Google ResearchArticle Google Research explanation

6. Grounded generation and knowledge artifacts

Baseline

6.1 Retrieval-Augmented Generation

Established concept

Retrieval-Augmented Generation (RAG) combines parametric model knowledge with non-parametric retrieved evidence. The production engineering problem is not only “retrieve then prompt”; it is to control identity, authorization, context sufficiency, prompt construction, output schema, attribution, and evaluation.

Tropos mechanism

governed retrieval → retrieval gate → EvidenceSet → sufficiency → structured generation request → schema-validated output → deterministic citation resolution → answer / artifact

Key architectural separation

Authorization, identity, versioning and deterministic business policy are resolved outside the model. The LLM is used for probabilistic synthesis, not as a reference monitor or system of record.

Validation

Groundedness, answer correctness, citation correctness/completeness, abstention quality, unsupported-claim rate, latency, token usage and human acceptance.

Paper Lewis et al. — Retrieval-Augmented GenerationTropos RAG architecture
Implemented baseline

6.2 Structured output as a typed artifact contract

Engineering concept

Schema-constrained generation narrows a generative model into a typed application boundary. The schema acts as a syntactic contract; application/domain validation then enforces stronger semantics.

Tropos technique

Knowledge Articles use fixed domain structures for Troubleshooting, How-to and FAQ artifacts rather than unconstrained Markdown. Provider output is validated against typed models before becoming a domain object.

Why this matters

  • Stable downstream rendering.
  • Deterministic validation of required fields.
  • Section-level and step-level evaluation.
  • Clear separation between “model produced parseable structure” and “content is correct.”

Extension: process diagrams

EvidenceSet → typed ProcessGraph {nodes[], edges[]} → graph validation → evidence reference validation → semantic evaluator → Mermaid/HTML renderer

The diagram should be generated from a validated intermediate graph rather than treating Mermaid syntax itself as the authoritative representation.

6.3 Artifact correctness: deterministic + semantic evaluators

Engineering concept

A generated artifact can be evaluated at multiple layers. Conflating them into one “LLM judge” hides failure causes.

1. schema validity 2. structural constraints 3. reference integrity 4. grounding / entailment 5. completeness 6. ordering / workflow semantics 7. style / readability 8. human acceptance

Example for a process diagram

  • Graph validity: every edge references existing nodes.
  • Topology rule: required start/end states, allowed cycles, reachability.
  • Evidence grounding: each action/decision node maps to evidence.
  • Semantic comparison: evaluator checks whether evidence supports the node/edge relationship.
  • Rendering: Mermaid parser succeeds after semantic graph approval.

Metrics

Structure pass rate, claim support rate, citation completeness, critical-step recall, ordering accuracy, reviewer edit distance/acceptance rate.

7. Security, authorization, and AI governance

Core invariant

7.1 Access-aware retrieval: reference monitor / complete mediation

Established security theory

Saltzer and Schroeder’s complete mediation principle requires checking authority on every access to every protected object. A reference monitor is the conceptual enforcement boundary through which access must pass.

Tropos mechanism

query + tenant/groups → canonical current-state eligibility → ACTIVE lifecycle check → tenant eligibility → restricted-group eligibility → only then ranking → governed evidence

Authorization is not delegated to prompt instructions and is not performed only after top-k retrieval. This prevents unauthorized candidates from occupying the ranking pool and treats access as a retrieval invariant.

Industry vocabulary

Tropos currently resembles a lightweight combination of tenant isolation and group-based RBAC/ABAC-style policy. A future hosted system would normally separate Policy Decision Point (PDP), Policy Enforcement Point (PEP), identities, and policy administration.

Standard NIST SP 800-162 — Attribute Based Access ControlPaper Saltzer & Schroeder — Protection of Information in Computer Systems
Local web baseline

7.2 Application security boundary

Industry framework

OWASP ASVS organizes verifiable application-security requirements across architecture, authentication, sessions, access control, input validation, cryptography, logging, data protection, APIs and configuration.

Tropos current controls

  • Loopback-only local binding.
  • Host validation to reduce DNS-rebinding exposure.
  • Origin validation for browser POSTs.
  • Random per-process request token.
  • Content-Type allow-listing.
  • Bounded file size/type handling.
  • Secrets excluded from browser diagnostics and repr.
  • Tenant/group authorization before retrieval.

Not yet equivalent to production authentication

The process token is a local request-protection mechanism, not user authentication, SSO, identity federation, MFA, or production session management.

7.3 Data egress and model-provider governance

Engineering problem

Remote embeddings, generation, evaluation and hosted observability can transmit governed data to external processors. Authorization to read data inside Tropos does not automatically imply authorization to export it to a provider.

Recommended mechanism

data object → classification / sensitivity → purpose + provider → egress policy decision ALLOW / DENY / REDACT / REQUIRE_APPROVAL → provider adapter → auditable egress event

Controls to consider

  • Provider allow-list.
  • Data-classification policy.
  • Redaction/tokenization.
  • Region/residency constraints.
  • Purpose limitation.
  • Cost/rate budgets.
  • Audit trail.

8. Testing, evaluation, and quality engineering

Strong baseline

8.1 Layered software verification

Engineering concept

Different tests provide evidence about different failure scopes. Line coverage alone cannot establish behavioral correctness.

Tropos layers

  • Unit tests: isolated rules, value objects, adapters.
  • Integration tests: persistence, ingestion, retrieval and local web/runtime boundaries.
  • Contract tests: shared expectations across interchangeable BM25/dense/hybrid retrievers.
  • Invariant tests: authorization, current-version, lifecycle and evidence integrity.
  • Negative tests: unsupported input, missing configuration, denied access, no-answer behavior.
  • Static typing: strict mypy.
  • Static analysis/formatting: Ruff.
  • Mutation sampling: evidence that assertions fail under deliberate behavioral mutations.

Technical distinction

Coverage answers what code executed; mutation testing asks whether tests detect changed behavior; contract tests ask whether alternative implementations satisfy one behavioral interface.

Pattern Fowler — Practical Test PyramidMethod Property-based testing overview
Strong baseline

8.2 Information-retrieval evaluation

Metrics and what they answer

  • Recall@k: did top-k contain expected relevant evidence?
  • Precision@k: what fraction of returned items are relevant?
  • MRR: how early does the first relevant item appear?
  • nDCG: how good is the ranking when relevance has multiple grades?
  • No-answer accuracy: does retrieval correctly avoid evidence when nothing is relevant?

Tropos experiment architecture

versioned EvalDataset → same cases → BM25 / dense / hybrid executors → observations + scores → EvalRun → baseline/candidate comparison → regression gate

Why same dataset matters

A strategy comparison is meaningful only when query set, expected evidence, corpus version and evaluation semantics remain controlled. Otherwise model/index changes are confounded with data changes.

Next rigor

Graded relevance labels, nDCG, larger independent cases, confidence intervals/bootstrap analysis, blind holdouts where feasible, and query-family correlation awareness.

Book Stanford IR — Evaluation in information retrievalTropos Evaluation product model
Growing

8.3 AI output evaluation

Evaluation decomposition

retrieval quality ≠ context sufficiency ≠ groundedness ≠ citation correctness ≠ answer correctness ≠ artifact completeness ≠ user outcome

This decomposition is critical: a correct answer can hide poor retrieval; excellent retrieval can feed an insufficient context; valid citations can point to evidence that does not entail the claim.

Recommended evaluator mix

  • Deterministic graders: schema, required fields, reference integrity.
  • Model-based graders: entailment, completeness, semantic correctness.
  • Human review: high-risk or ambiguous quality decisions.
  • Product outcome metrics: acceptance, edits, reuse, resolution success.

Quality control

LLM-as-judge should itself be versioned and calibrated against human labels; it should not be treated as objective ground truth.

8.4 Regression gating and change evidence

Engineering concept

A quality gate converts measured behavior into a release decision. The important distinction is between zero-tolerance invariants (e.g., authorization leakage) and degradable quality metrics (e.g., small recall change).

Tropos mechanism

Baseline and candidate EvalRuns are compared under fixed dataset/provenance. Hard invariant failures remain release-blocking; retrieval-quality movement is interpreted under explicit tolerances rather than mixed with security correctness.

Related deployment pattern

This is analogous to continuous verification: CI tests source correctness while evaluation gates check AI-system behavior under representative cases.

9.2 Performance engineering

Established measures

  • Latency distribution: p50, p95, p99 rather than mean alone.
  • Throughput: requests/operations per second.
  • Concurrency: simultaneous in-flight work.
  • Saturation: degree to which a constrained resource is fully utilized.
  • Capacity: maximum sustainable load under SLOs.

Tropos current evidence

Stage latency is captured and exact vector search provides a clean baseline, but the system does not yet have production-scale load/capacity evidence.

Scale rehearsal

10k → 50k → 100k → 500k chunks for each scale: BM25 latency exact vector latency memory/storage concurrent queries p50/p95/p99 retrieval quality unchanged? → introduce ANN only when target violated

Tail latency

Distributed systems are often governed by the slow tail rather than the average request. Provider latency, retrieval, retries and fan-out can compound at high percentiles.

Partial

9.3 Reliability and resilience

Established mechanisms

  • Timeout: bound dependency wait time.
  • Retry: repeat transient failures only when operation semantics allow it.
  • Exponential backoff + jitter: avoid synchronized retry storms.
  • Circuit breaker: stop repeated calls to an unhealthy dependency.
  • Idempotency: repeated request does not create unintended duplicate state.
  • Bulkhead/backpressure: limit failure propagation/resource exhaustion.
  • Graceful degradation: preserve safe partial capability.

Tropos today

Provider timeouts, explicit fail-closed errors, idempotent ingestion/materialization and BM25 independence provide part of this foundation. General retry/backoff/circuit-breaker policies are not yet systemic.

Reliability metrics

Availability, error rate, dependency failure rate, retry rate, recovery time, SLO attainment, and eventually RTO/RPO for durable production state.

10. Architecture and maintainability

Strong

10.1 Modular monolith + Ports and Adapters

Established concept

Hexagonal Architecture / Ports and Adapters keeps application/domain rules independent from transport, database, model provider and external service technologies. A modular monolith retains one deployable unit while imposing internal module boundaries.

Tropos mapping

  • tropos.core owns reusable source, knowledge, retrieval, evidence and evaluation mechanics.
  • Capabilities such as Resolve own domain-specific business semantics.
  • LLM, embeddings, persistence, source connectors and retrievers implement Tropos-owned ports.
  • Frameworks/providers remain adapters rather than domain owners.

Engineering benefit

Replaceability can be tested: BM25, dense and hybrid implement the same retrieval contract; model providers can be swapped without changing Knowledge Article domain objects.

Trade-off

Tropos maintains explicit orchestration and adapter code instead of outsourcing architecture to a framework. This costs code but keeps governance and domain semantics visible.

Strong

10.2 Architecture decisions and strategy versioning

Established concept

Architecture Decision Records (ADRs) retain the context, decision, alternatives, consequences and revisit conditions behind durable technical choices.

Tropos mechanism

Algorithm identity is also made explicit through strategy versions: normalizer version, chunker version, retrieval strategy, embedding strategy and processing version. This converts algorithm changes into observable lineage rather than invisible implementation drift.

Why strategy versioning matters

AI/data systems can change behavior without changing business input. Recording the algorithm/configuration identity supports replay, comparison, migration, rollback and audit.

11. Reading the map as an engineering system

Capability is not mechanism

“Semantic retrieval” is a capability. “OpenAI embeddings + exact cosine search” is the present mechanism. “HNSW in pgvector” is a possible scale mechanism. The capability should remain stable while implementations can be replaced under explicit contracts.

Correctness is not one metric

Security invariants, retrieval relevance, evidence sufficiency, citation entailment, generated-artifact structure, latency, reliability, and user outcomes require different evidence. A mature architecture keeps these quality questions separate and composes them into release decisions.

Derived state should remain replaceable

Search indexes, embeddings, fused rankings, telemetry projections and rendered artifacts are reproducible representations. Canonical source/capture identity, governed knowledge, policy state and stable evidence references provide the durable backbone from which those representations can be rebuilt.
